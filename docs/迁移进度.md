peer 声明不可能与新 Angular 同时满足。**这是迁移期的临时措施，迁移完应删除。**

### 执行方式

1. 先把 Clarity / `ngx-markdown` 手工改到 v9 兼容版本；
2. 再跑官方迁移：`ng update @angular/cli@9 @angular/core@9 --allow-dirty`（约 9.5 分钟）。

顺序不能反：`ng update` 不认识 Clarity，若不预改，`npm install` 阶段会被 Clarity 2 的
peer 声明卡死。

### 官方迁移实际改了什么

- **`dynamic-queries`**：**移除** `@ViewChild/@ContentChild` 上的 `{ static: false }`。
  v9 起 `static: false` 已是默认值，**行为等价**；`{ static: true }` 共 60 处**全部保留未动**。
  > 事前估算「355 处 ViewChild 要补 `{static}`」是**错的**：347 处早在 v8 迁移时就已带 `{static}`，
  > 剩下 8 处是 4 处注释 + 4 处 `@ContentChildren`（本就不接受 `static`）。这一跳的人工面≈0。
- **`undecorated-classes-with-di`**：给带 DI 的未装饰基类补 `@Directive()`（11 处）、`@Injectable()`（5 处）。
- **`@angular/cli` 迁移**：`angular.json`、`tsconfig.json`、`src/tsconfig.app.json`、`src/tsconfig.spec.json`。

源码净改动 **374 增 / 336 删**。
> 注意：`package-lock.json` 会把 diff 放大成「15785 增 / 9340 删」的假象，**看 diff 一律排除它**。

### Ivy 模板类型检查暴露并修复的既有缺陷

`tsconfig.json` 的 `fullTemplateTypeCheck: true` **在 v8 时就已开着**，只是 ViewEngine 查不出来、Ivy 查得出来。
这 3 处是**真 bug，不是升级引入的**：

1. `src/app/portal/ingress/ingress.component.html:26`
2. `src/app/portal/autoscale/autoscale.component.html:27`

   两处都调用 `listPublishHistory()`，而该方法已在 `9efa209「清除portal组件」`中
   **连同实现**（`this.publishHistoryService.openModal(this.publishType, this.resourceId)`）
   **一起删除**，`PublishHistoryService` 与对应组件也已不存在。
   两个「发布历史」按钮成为**残留死代码** —— 在 v8 下点击必然抛错。
   处置：**移除按钮**，完成那次没做完的清理。（若日后要恢复该功能，需重建 service + 组件，
   不是加个方法就够。）

3. `src/app/admin/kubernetes/event/list-event/list-event.component.html:54`

   模板直接引用全局 `Object.keys(...)`，v9 起模板不允许引用全局对象。
   处置：把原表达式**逐字**移入组件方法 `hasNoLabels(obj)`，语义（含短路顺序）完全一致。
   > 曾先试 `(labels | keyvalue).length`，报 `TS2531`：`KeyValuePipe` 有返回 `null` 的重载，
   > 输入为 `any` 时 TS 会挑中它。**不要赌类型收窄，改成普通 TS 方法最稳。**

## 跳 1 回归修复：行内固定列白底盖住斑马纹（2026-10-10）

**现象**：列表页同一行出现两个颜色——最左侧固定列（⋮ 操作列）发白，行身是斑马纹色
（像素实测：白条 x=17..65 为 #ffffff，行身 x=66+ 为 #f5f7fb）。

**根因**：Clarity 3 行结构新增 `.datagrid-row-sticky` 容器（position: sticky、z-index 500、
包裹 select/action/caret 等固定列单元格），自带不透明白底
`background-color: var(--clr-table-bgcolor)`（= white），把项目斑马纹
`.datagrid-table clr-dg-row:nth-child(odd)`（打在 clr-dg-row 宿主上）盖住了。
v2 无此容器，行背景直接透出，故整行一色。

**修复（v2 修订）**：styles.scss 末尾追加同选择器维度的对齐规则——
`.datagrid-table clr-dg-row:nth-child(odd):not(.datagrid-selected):not(:hover) .datagrid-row-sticky`
背景色设为**不透明** `#f5f7fb`。初版用 `rgba(232,237,246,.45)` 有残留色差：sticky 叠在
行宿主斑马纹之上，半透明色二次叠加合成出 #f0f3f9，与行身 #f5f7fb 肉眼可辨（用户实测反馈）。
改用斑马纹在白底上的等效合成色后，Chromium 实测 sticky rgb(245,247,251) 与行身逐通道一致。
偶数行行身白底、sticky 白底天然一致。

**修复（v3 修订，hover 态）**：初版规则带 :not(:hover)，悬停时让位给 Clarity 的
`.datagrid-row:hover .datagrid-row-sticky`（#e8e8e8），而行身斑马纹 (0,2,1) 压过
行宿主 hover (0,2,0) 保持不变——悬停时反而出现 sticky #e8e8e8 vs 行身 #f5f7fb 的断层。
去掉 :not(:hover)（特异性 (0,4,1) 压过 Clarity sticky hover (0,3,0)），悬停时 sticky
与行身同保持斑马纹色，与 v2 悬停表现一致；选中态仍由 .datagrid-selected 交还 Clarity。

**验证**：dart-sass 编译通过；用 Playwright Chromium 加载编译后样式 + 复刻 v3 行 DOM
实测：修复前 sticky 计算背景 rgb(255,255,255)，修复后 rgba(232,237,246,.45) 与行宿主一致，
截图确认整行无色差。

**注**：v3 行是 `.datagrid-table` 的直接子元素（表头占第 1 个子节点），
nth-child 计数与 v2（行包裹在 .datagrid-body 内）相比整体偏移 1，
斑马纹相位可能与 v2 相差一行；因 sticky 对齐规则与斑马纹共用同一选择器，两者始终一致。

## 跳 1 回归修复：表格边框复现（2026-10-10）

**现象**：升级 Clarity 2→3 后，列表页数据网格重新出现行边框/表头下边框（原有外观为无边框 + 斑马纹）。

**根因**：Clarity 3 默认开启 `$clr-use-custom-properties: true`，`_properties.tables.scss` 把边框色、
表头底色在 `:root` 处固化为字面量引用（如 `--clr-table-border-color: var(--clr-color-neutral-400)`），
`custom.scss` 里的 SCSS 变量覆盖（`transparent`/`#e8edf6`）随之全部失效。旧变量名
`$clr-table-bordercolor`、`$clr-table-borderstyle` 在 v3 中也已不存在。

**修复**：`src/styles.scss` 末尾（Clarity 导入之后）新增 `:root` 覆盖块，重设
`--clr-table-border-color` / `--clr-table-header-border-bottom-color` /
`--clr-table-footer-border-top-color` / `--clr-tablerow-bordercolor` 为 `transparent`，
`--clr-thead-bgcolor` 为 `#e8edf6`；`custom.scss` 加注释说明 SCSS 变量覆盖已失效。

**验证**：dart-sass 编译 `styles.scss` 通过；编译产物中覆盖块（pos 641158）位于 Clarity
`:root`（pos 457692）之后，同特异性后者被覆盖；`.datagrid-row` 边框消费点解析为
`var(--clr-table-border-color)` → transparent，表头底色恢复 `#e8edf6`。
