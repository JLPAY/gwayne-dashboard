新增 `.npmrc`（`legacy-peer-deps=true` 等）：老生态（`@angularclass/hmr`、xterm 3.x、prismjs…）的
peer 声明不可能与新 Angular 同时满足。**这是迁移期的临时措施，迁移完应删除。**

### 执行方式

1. 先把 Clarity / `ngx-markdown` 手工改到 v9 兼容版本；
2. 再跑官方迁移：`ng update @angular/cli@9 @angular/core@9 --allow-dirty`（约 9.5 分钟）。

顺序不能反：`ng update` 不认识 Clarity，若不预改，`npm install` 阶段会被 Clarity 2 的
peer 声明卡死。

### 官方迁移实际改了什么

- **`dynamic-queries`**：**移除** `@ViewChild/@ContentChild` 上的 `{ static: false }`。
  v9 起 `static: false` 已是默认值，**行为等价**；`{ static: true }` 共 60 处**全部保留未动**。
  > 事前估算「355 处 ViewChild 要补 `{static}`」是**错的**：347 处早在 v8 迁移时就已带 `{static}`，
  > 剩下 8 处是 4 处注释 + 4 处 `@ContentChildren`（本就不接受 `static`）。这一跳的人工面≈0。
- **`undecorated-classes-with-di`**：给带 DI 的未装饰基类补 `@Directive()`（11 处）、`@Injectable()`（5 处）。
- **`@angular/cli` 迁移**：`angular.json`、`tsconfig.json`、`src/tsconfig.app.json`、`src/tsconfig.spec.json`。

源码净改动 **374 增 / 336 删**。
> 注意：`package-lock.json` 会把 diff 放大成「15785 增 / 9340 删」的假象，**看 diff 一律排除它**。

### Ivy 模板类型检查暴露并修复的既有缺陷

`tsconfig.json` 的 `fullTemplateTypeCheck: true` **在 v8 时就已开着**，只是 ViewEngine 查不出来、Ivy 查得出来。
这 3 处是**真 bug，不是升级引入的**：

1. `src/app/portal/ingress/ingress.component.html:26`
2. `src/app/portal/autoscale/autoscale.component.html:27`

   两处都调用 `listPublishHistory()`，而该方法已在 `9efa209「清除portal组件」`中
   **连同实现**（`this.publishHistoryService.openModal(this.publishType, this.resourceId)`）
   **一起删除**，`PublishHistoryService` 与对应组件也已不存在。
   两个「发布历史」按钮成为**残留死代码** —— 在 v8 下点击必然抛错。
   处置：**移除按钮**，完成那次没做完的清理。（若日后要恢复该功能，需重建 service + 组件，
   不是加个方法就够。）

3. `src/app/admin/kubernetes/event/list-event/list-event.component.html:54`

   模板直接引用全局 `Object.keys(...)`，v9 起模板不允许引用全局对象。
   处置：把原表达式**逐字**移入组件方法 `hasNoLabels(obj)`，语义（含短路顺序）完全一致。
   > 曾先试 `(labels | keyvalue).length`，报 `TS2531`：`KeyValuePipe` 有返回 `null` 的重载，
   > 输入为 `any` 时 TS 会挑中它。**不要赌类型收窄，改成普通 TS 方法最稳。**

## 跳 1 回归修复：行内固定列白底盖住斑马纹（2026-10-10）

**现象**：列表页同一行出现两个颜色——最左侧固定列（⋮ 操作列）发白，行身是斑马纹色
（像素实测：白条 x=17..65 为 #ffffff，行身 x=66+ 为 #f5f7fb）。

**根因**：Clarity 3 行结构新增 `.datagrid-row-sticky` 容器（position: sticky、z-index 500、
包裹 select/action/caret 等固定列单元格），自带不透明白底
`background-color: var(--clr-table-bgcolor)`（= white），把项目斑马纹
`.datagrid-table clr-dg-row:nth-child(odd)`（打在 clr-dg-row 宿主上）盖住了。
v2 无此容器，行背景直接透出，故整行一色。

**修复（v2 修订）**：styles.scss 末尾追加同选择器维度的对齐规则——
`.datagrid-table clr-dg-row:nth-child(odd):not(.datagrid-selected):not(:hover) .datagrid-row-sticky`
背景色设为**不透明** `#f5f7fb`。初版用 `rgba(232,237,246,.45)` 有残留色差：sticky 叠在
行宿主斑马纹之上，半透明色二次叠加合成出 #f0f3f9，与行身 #f5f7fb 肉眼可辨（用户实测反馈）。
改用斑马纹在白底上的等效合成色后，Chromium 实测 sticky rgb(245,247,251) 与行身逐通道一致。
偶数行行身白底、sticky 白底天然一致。

**修复（v3 修订，hover 态）**：初版规则带 :not(:hover)，悬停时让位给 Clarity 的
`.datagrid-row:hover .datagrid-row-sticky`（#e8e8e8），而行身斑马纹 (0,2,1) 压过
行宿主 hover (0,2,0) 保持不变——悬停时反而出现 sticky #e8e8e8 vs 行身 #f5f7fb 的断层。
去掉 :not(:hover)（特异性 (0,4,1) 压过 Clarity sticky hover (0,3,0)），悬停时 sticky
与行身同保持斑马纹色，与 v2 悬停表现一致；选中态仍由 .datagrid-selected 交还 Clarity。

**验证**：dart-sass 编译通过；用 Playwright Chromium 加载编译后样式 + 复刻 v3 行 DOM
实测：修复前 sticky 计算背景 rgb(255,255,255)，修复后 rgba(232,237,246,.45) 与行宿主一致，
截图确认整行无色差。

**注**：v3 行是 `.datagrid-table` 的直接子元素（表头占第 1 个子节点），
nth-child 计数与 v2（行包裹在 .datagrid-body 内）相比整体偏移 1，
斑马纹相位可能与 v2 相差一行；因 sticky 对齐规则与斑马纹共用同一选择器，两者始终一致。

## 跳 1 回归修复：表格边框复现（2026-10-10）

**现象**：升级 Clarity 2→3 后，列表页数据网格重新出现行边框/表头下边框（原有外观为无边框 + 斑马纹）。

**根因**：Clarity 3 默认开启 `$clr-use-custom-properties: true`，`_properties.tables.scss` 把边框色、
表头底色在 `:root` 处固化为字面量引用（如 `--clr-table-border-color: var(--clr-color-neutral-400)`），
`custom.scss` 里的 SCSS 变量覆盖（`transparent`/`#e8edf6`）随之全部失效。旧变量名
`$clr-table-bordercolor`、`$clr-table-borderstyle` 在 v3 中也已不存在。

**修复**：`src/styles.scss` 末尾（Clarity 导入之后）新增 `:root` 覆盖块，重设
`--clr-table-border-color` / `--clr-table-header-border-bottom-color` /
`--clr-table-footer-border-top-color` / `--clr-tablerow-bordercolor` 为 `transparent`，
`--clr-thead-bgcolor` 为 `#e8edf6`；`custom.scss` 加注释说明 SCSS 变量覆盖已失效。

**验证**：dart-sass 编译 `styles.scss` 通过；编译产物中覆盖块（pos 641158）位于 Clarity
`:root`（pos 457692）之后，同特异性后者被覆盖；`.datagrid-row` 边框消费点解析为
`var(--clr-table-border-color)` → transparent，表头底色恢复 `#e8edf6`。

## 2-pre：清除 rxjs-compat 深路径导入

提交：`ec82957`　前置：`3af4891`

### 实测工作面（比方案文档的估算更细）

| 形态 | 数量 | 说明 |
|---|---:|---|
| `import 'rxjs/add/*'` | 264（src 248 + lib 16） | 其中 52 处 `rxjs/add/observable/*` 是**纯死导入**（`Observable.throw/combineLatest/fromPromise` 均未被调用） |
| `rxjs/Subscription` `rxjs/Observable` `rxjs/Subject` 深路径命名导入 | 161 | 归一到 `'rxjs'` 并合并重复导入 |
| 需改 `.pipe()` 的补丁操作符链 | **4** | 全在 `dual-list-box.component.ts`（`debounceTime` + `distinctUntilChanged`） |

**方案文档漏记的一点**：项目有**两棵源码树** `src/` 与 `lib/`（30 个 .ts）。只扫 `src/` 会让构建在
`lib/portal/service/...` 处报 `has no exported member 'Subscription'`。codemod 必须同时覆盖 lib。

### 为什么必须类型检查、不能正则

`.map(` 全仓 104 处，其中**只有 4 处**是 Observable 语义；其余是 `Array.prototype.map`
（`Object.getOwnPropertyNames(...).map`、`resp.data.map` 等）。`.catch(` 9 处全是 `Promise.catch`。
正则改写会直接改坏业务逻辑。判定方式：`checker.getPropertyOfType(getTypeAtLocation(call), 'subscribe')`。
另有 30 处接收者类型为 `any` 的调用点（类型擦除），已**逐个核对**为 HTTP 响应 `data`、`[].slice.call(...)`、
`this.currentForm.controls.clusters.value` 等数组，无隐藏 Observable。

### 工具与踩坑（重要）

- 新增 `tools/codemod-rxjs-compat.js`：类型检查驱动，多轮收敛（处理嵌套链的编辑冲突），
  **写盘前对产出做语法自检**（`ts.createSourceFile` 的 `parseDiagnostics`），失败即拒绝写入。
- 新增 `tools/diag-rxjs-operators.js`：打印每个 `.map/.catch/...` 的**接收者类型**，用于拿到真实基数。
- **踩坑（已修复）**：codemod 第一版先把 CRLF 折成 LF 再套用 TypeScript 给的偏移量，
  由于偏移量基于原始文本，每跨一行就前移一个字符 → 编辑落到别的代码上，把 `import` 吃掉。
  处置：一律用**原始文本**参与计算，写回前再统一行尾；并加语法自检兜住这类事故。
  （本次靠 `git checkout -- src/` 完整回滚，未产生残留。）
- 同一文件多条 `rxjs` 根导入时，「合并删除」与「深路径改名」的编辑范围会重叠 →
  先算删除集合、被删语句不再单独改名。

## 2a 回归修复：展开行详情被固定列顶到右侧（2026-10-12）

提交：`5f79753`　现象提出：CRD / Service 等带 `*clrIfExpanded` 展开行的列表

**现象**：展开行的详情子列表不再通栏顶左 —— 内容整体被挤到右侧，最左「操作列 + 展开箭头」
两个固定列的位置留出空白，首格文字还被固定列的不透明白底裁掉一截。

**定位**：模板与 SCSS 自最初提交 `f739a54` 起**从未改动**，问题全部来自 Clarity 2.4.11 → 4.0.16
的 datagrid 结构代差：

- `.datagrid-row-flex` 的 `flex-direction` 由 `column nowrap`（v2）改为 `row nowrap`（v4）；
- 行内固定列（操作列 + 展开箭头，各 1.9rem）移入新增的 `.datagrid-row-sticky` 容器
  （`position: sticky`、`z-index: 502`，自带不透明白底、随行拉伸全高）；
- `*clrIfExpanded` 的详情从 `.datagrid-row-flex` 的直接子元素，移进右侧的 `.datagrid-row-scrollable`。

夹具实测偏移：详情 `left` 0 → 76px、内容起点 50 → 126px、嵌套表宽 1038 → 962px。

**修复**：`src/styles.scss` 末尾追加（仅命中带 `.datagrid-container` 的自定义详情，
全仓未使用 Clarity 自身的 `clrDgReplace` 模式，故不影响它）：

```scss
.datagrid-row .datagrid-row-scrollable .datagrid-row-detail.datagrid-container {
  margin-left: -3.8rem;   // 抵消 2 个固定列宽（2 × 1.9rem）；详情是 scrollable 的
                          // stretch 项，负左 margin 会自动把宽度撑回全行宽，无需写 width
  position: relative;
  z-index: 503;           // 抬过 sticky 的 z-index:502 不透明白底
}
```

只加负 margin 是不够的：详情左缘 76px 会被 sticky 的不透明白底盖住
（实测嵌套表首格 `demo-instance` 只剩 `o-Instance`），故补 `position: relative` + `z-index: 503`。

**验证**：

| 项 | 结果 |
|---|---|
| 端到端观感比对 | ✅ 取 `@clr/angular@2.4.11` 的真实行模板拼 DOM 夹具 + Clarity 4 生产构建的 `styles.css`，Playwright Chromium 实测：详情距行左 0px、宽 1100px、内容起点 50px、嵌套表 1038px，与最初（v2）逐项一致 |
| 层叠断言 | ✅ `elementFromPoint` 命中详情单元格而非 sticky |
| 三层门禁 | ✅ 全绿（契约 151/331/314/351、模板 226/243/10/95/38、参数等价 93240） |

### 手工修复

1. **`tools/verify-param-equivalence.js` 被 v13 打破（真回归，必修为）**

   Angular 13 **移除 UMD 包**后，`@angular/*` 的 `package.json` **没有 `main`**，
   `exports` 全量指向 `fesm2015/*.mjs`（**纯 ESM，无任何 CJS 入口**）。
   而 Node 22 支持 `require(ESM)`，于是夹具里那句
   `const { HttpParams } = require('@angular/common/http')` **真的去加载 ESM 链**：
   `http.mjs` → `@angular/core/fesm2015/core.mjs`，而 core.mjs 里有
   `import { ... } from 'rxjs/operators'` —— rxjs 6.x 是 CJS 包、无 `exports` 映射，
   ESM 解析器遇到**目录导入**直接抛：

   ```
   ERR_UNSUPPORTED_DIR_IMPORT: Directory import '.../node_modules/rxjs/operators'
     is not supported resolving ES modules imported from .../core.mjs
   ```

   绕过目录导入后还有第二关：Angular 12 起发布的包是**部分编译（partial compilation）**格式，
   运行时遇到 `ɵɵngDeclareFactory` 会去 `global.ng.ɵcompilerFacade` 找 JIT 编译器，
   拿不到就抛「needs to be compiled using the JIT compiler」。

   **处置**：
   - 新增 `tools/esm-dir-import-loader.mjs`：只在 `ERR_UNSUPPORTED_DIR_IMPORT` 时重试一次，
     把 specifier 补成 `<spec>/index.js`；不改变其它任何解析行为。
   - 夹具内先 `require('@angular/compiler')`（它加载时会注册 `ng.ɵcompilerFacade`），
     再 `require('@angular/common/http')`。
   - **不改变比对对象**：这两步只影响 DI 元数据的生成方式，`HttpParams.toString()` 行为不变
     （比对仍是 93240 用例逐字节一致）。

2. **`tools/patch-esbuild-native-check.js` 改为版本无关**

   v13 把探测代码从裸 `child_process_1.spawnSync(process.execPath, [...])`
   改成 `try { (0, child_process_1.spawnSync)(...) } catch { return false; }` ——
   缩进与调用形态都变了，旧的**精确字符串匹配**随之失效（脚本按设计**拒绝盲写**，exit 3）。
   处置：改为「定位 `static hasNativeSupport()` → **花括号配对**取出方法体 → 整段替换」，
   替换前校验方法体确实含 `spawnSync`（避免配错位置）；并补 `.unpatched` 原文备份，
   使 `--revert` 能精确还原（不再依赖硬编码的原始文本）。
   已实测闭环：应用 → 幂等跳过 → 精确还原 → 再应用，四步全通过。

3. **`tools/normalize-eol.js` 作用域补齐根目录文件**

   它的 `INCLUDE` 原本只覆盖 `src|lib|tools|e2e|docs/`，**根目录文件被排除**；

   处置：把**根目录单层文本文件**（`angular.json`、`README.md`、`.gitignore` 等）纳入范围。

4. `.gitignore` 追加 `.tmp-smoke/`（`tools/smoke-runtime.js` 的截图产物）。

## 环境与工具（本机踩坑，非项目问题）

这几条是本机（Windows + 沙箱 + Node 22）特有的，每次迁移都会撞到，务必先看：

1. **`ng update` 在本机稳定失败**：它要装「临时 CLI」，走到 `spawnSync cmd.exe` 就报
   `EBUSY`（**脱沙箱重试同样失败，非偶发**）。
   → 等效替代流程：**手工改 package.json 版本 + `npm install`**，再用已装好的新 CLI 跑
   `ng update <pkg>@N --migrate-only --from=<N-1> --to=N --allow-dirty`。
   注意 v10 CLI 的开关是 `--migrate-only`（`--migrations-only` 会被当成包名报错）。
2. **`npm install` 前必须停掉 dev server**：webpack watcher 占着 `node_modules/@clr/*` 的文件，
   npm 删除时会报 `[safe-delete] ... trash operation ... aborted`。
   查端口占用：`netstat -ano | grep :4200`，杀进程：`MSYS_NO_PATHCONV=1 taskkill /F /PID <pid>`。
3. **生产构建（`--prod`）必须在沙箱外跑**：v10+ 的 ES5 差分加载会走 babel-loader 写
   `babel-webpack` 缓存，该写入被沙箱拦成 `EPERM: operation not permitted, open '...json'`。
   已用 `NG_BUILD_CACHE=<绝对路径>` 验证过**与缓存路径无关**（换到系统临时目录仍失败），是写入策略问题。
   dev 构建（`ng build`）不受影响。
4. **运行时冒烟**：`tools/smoke-runtime.js`（Playwright Chromium）。
   本机 Edge 被安全策略静默拦截（连 `--version` 都无输出），所以用 Playwright 自带的 chromium
   （`%LOCALAPPDATA%/ms-playwright`，npmmirror 源下载）。
   用法（需先把 Playwright 装在托管 workspace，再用 NODE_PATH 指向它）：
   ```
   cd <workspace> && NODE_PATH=<workspace>/node_modules node <项目>/tools/smoke-runtime.js [url]
   ```
   判据：页面渲染出应用 DOM、**无未捕获异常**。后端不可达导致的 401/连接失败不算失败。
5. **webpack 必须与 `build-angular` 的 pin 完全一致（v12 起）**：
   `build-angular@12.2.18` 钉死 `webpack: 5.50.0`，且 `@angular-devkit/build-webpack` 会
   `require('webpack')`。根依赖**不要**写 `^5.x`：那样会被解析到 5.111.1 并提升到根，
   同时在 build-angular 下再装一份 5.50.0 → **双实例**。一律写**精确版本**。
   教训：`^` 在「上游 pin 精确版本」的场景下反而是隐患。
6. **`--max_old_space_size` 不要给太大，但也别指望它能消除段错误**：
   v12 时 webpack 5 + 完整优化叠加 **8GB 堆**会**稳定**触发 V8 段错误（exit 139），
   降到 4096 即通过，故脚本统一用 **4096**。
   **但 v13 起发现段错误是间歇性的**（4096 下 8 次里崩 1 次，2048/3072/4096 都能通过，
   与堆上限无单调关系）—— 见「2d」一节的排查留痕。
   **诊断特征：无 JS 异常、无 webpack/TS 报错，只有 `Segmentation fault`（exit 139）→ 先重跑。**
   > 别用 `--build-optimizer=false` 绕过——那会关掉真实优化，产物会显著变大。
7. **`tools/patch-esbuild-native-check.js` 每次 `npm install` 后都要重跑**：
   本机 `spawnSync` 恒 EBUSY → Angular 12 的 esbuild 原生探测失败 → 回落 esbuild-wasm，
   而 esbuild-wasm 在本机也失败 → **生产构建做不出来**。该补丁幂等、带标记、支持 `--revert`。
8. **Angular 13 移除 UMD 后，`require('@angular/*')` 会走 ESM 链**（Node 22 支持 require(ESM)）：
   `@angular/*` 的 `exports` 全指向 `fesm2015/*.mjs`、**无任何 CJS 入口**。
   于是任何用 `require()` 加载 Angular 的 **Node 侧脚本**都会踩两个坑：
   (a) ESM 不支持**目录导入** → `rxjs/operators` 抛 `ERR_UNSUPPORTED_DIR_IMPORT`；
   (b) 部分编译格式需要 JIT facade → 不先加载 `@angular/compiler` 就抛
   「needs to be compiled using the JIT compiler」。
   → 处置见 `tools/esm-dir-import-loader.mjs` 与 `tools/verify-param-equivalence.js` 的注释。
   **以后新写 Node 侧夹具/脚本、且要 import Angular 时，直接把这两步抄过去。**
